One database. One identity. Three completely different UIs. Here's how to make a custom React frontend, a Python API, and a Microsoft PowerApps canvas app all sing from the same songbook — without anyone losing their minds.

What you'll build: a small Task Tracker app where developers see a slick React UI, business users open a no-code PowerApps screen, both hit the same FastAPI backend, both store data in Microsoft Dataverse, and everybody signs in with their work email exactly once.

Why this combination is actually useful

If you've ever worked at a company that runs on Microsoft 365, you already know the tension: the dev team wants React because it's fast and flexible, the data engineers want Python because every integration in the world has a Python SDK, and somebody in operations swears the next project should be a PowerApps canvas app because they built one last quarter in an afternoon.

The good news: you don't have to choose. With Microsoft Entra ID as the single identity layer and Microsoft Dataverse as the single source of truth, all three play together remarkably well.

The architecture, in one picture

                |                              |
       Bearer JWT (MSAL)            Native or custom connector

        +-----------------+                    |
        | FastAPI backend |<-------------------+
        +-----------------+

                v
        Microsoft Dataverse  (cr123_tasks table)

Two UI paths converge on one Dataverse table. Entra ID hands out tokens that every layer trusts. That's the whole magic.

Step 1 — Set up Entra ID (the part everyone skips and regrets)

You need two app registrations in Microsoft Entra Admin Center:

  • Task Tracker API — confidential client (has a secret), exposes a scope called access_as_user, holds permissions to call Dataverse.
  • Task Tracker SPA — public client (browser), with a single-page redirect URI of http://localhost:5173, granted delegated access to that access_as_user scope.

Don't forget the magic button: Grant admin consent. Skipping this is the #1 cause of AADSTS65001 errors. Decode any troublesome token at jwt.ms — 80% of auth bugs are obvious once you see the claims.

Step 2 — The FastAPI backend

The whole token-validation story is nine lines thanks to fastapi-azure-auth:

from fastapi_azure_auth import SingleTenantAzureAuthorizationCodeBearer

azure_scheme = SingleTenantAzureAuthorizationCodeBearer(
    app_client_id=API_CLIENT_ID,
    tenant_id=TENANT_ID,
    scopes={f"api://{API_CLIENT_ID}/access_as_user": "access_as_user"},
)

For Dataverse, FastAPI gets its own app-only token via the confidential MSAL client:

app = msal.ConfidentialClientApplication(
    client_id=API_CLIENT_ID,
    client_credential=API_CLIENT_SECRET,
    authority=f"https://login.microsoftonline.com/{TENANT_ID}",
)
token = app.acquire_token_for_client(scopes=[f"{DATAVERSE_URL}/.default"])

From there it's just OData v4 calls against /api/data/v9.2/cr123_tasks.

Step 3 — The React 19 frontend

MSAL React turns sign-in into a two-line affair:

import { MsalProvider } from "@azure/msal-react";
import { PublicClientApplication } from "@azure/msal-browser";

const instance = new PublicClientApplication(msalConfig);
await instance.initialize();   // required in MSAL v3+

<MsalProvider instance={instance}>
  <App />
</MsalProvider>

Then calling the API is just acquireTokenSilent + fetch:

const result = await instance.acquireTokenSilent({
  scopes: [`api://${API_CLIENT_ID}/access_as_user`],
  account: instance.getActiveAccount(),
});

await fetch(`${apiBase}/api/tasks`, {
  headers: { Authorization: `Bearer ${result.accessToken}` },
});

Step 4 — PowerApps, the easy mode

Here's the part that always surprises developers: PowerApps doesn't need your API for basic CRUD. The native Dataverse connector talks directly to the same cr123_tasks table, and the user is already signed in to Power Apps via Entra ID. One formula and you have a working data grid:

Sort(
  Filter(Tasks, ddStatus.Selected.Value = "All"
                || cr123_status = ddStatus.Selected.Value),
  cr123_duedate
)

Use a custom connector (import your FastAPI's /openapi.json) only when you need PowerApps to go through your Python business logic — for example, a custom validation rule that you don't want to duplicate in Power Fx.

The "aha" moments

  • One identity, three UIs. The same user, the same access, three completely different rendering surfaces.
  • The token's aud claim is the contract. FastAPI trusts a token only if its audience matches the API's client id. That's why you need two app registrations.
  • Dataverse gives you free RBAC. Security roles on the table apply whether the request comes from React, FastAPI, or PowerApps.
  • jwt.ms is your best friend. Most auth pain disappears the moment you actually read the token.

What's next

This pattern scales surprisingly well. From here you can:

  • Add a Power Automate flow that emails the assignee when a task is created — zero extra code in FastAPI.
  • Add server-side role-based access in FastAPI by reading the roles claim from the JWT.
  • Deploy: React to Azure Static Web Apps, FastAPI to Azure Container Apps, PowerApps stays in the Power Platform.
